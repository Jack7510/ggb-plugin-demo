# 收尾讲解：沿一次请求看懂 GeoGebra 工程

本文用于各段开发视频之后的串讲，建议录制约 7 分 30 秒。
面向已经看过开发过程、希望理解整体设计并继续阅读代码的同事。

本文是录制提纲与口述稿，不新增接口、验收规则或完成声明。
架构、流程和状态图复用现有文档；讲解时只放大当前需要解释的部分。
更短的概述可参考[三分钟总结提纲](summary-video.md)。

## 1. 讲解目标与贯穿主线

以完整三角形请求贯穿讲解。观众看完应能回答三个问题：

1. 谁负责理解要求，谁负责执行数学，谁决定可以交付？
2. 为什么结果可信，怎样从产物追溯请求和事实？
3. 换一道题时，哪些内容改变，哪些模块继续复用？

贯穿主线是：

> 用户要求 → Agent 按 Skill 保存请求 → CLI 预检并调用 GeoGebra →
> 采集事实与核验 → 导出、独立重载和适用交互 → 清理并提交交付 → 同文件预览。

用三类数据组织说明：**请求声明了什么、引擎实际产生了什么、交付最终保存了什么。**
先让观众看到一条完整链路，再按问题定位代码。

## 4. 分段口述稿与画面切换

### 4.1 开场：把前面的片段连成一条链

**画面。** 打开[架构图](arch.md#架构与责任)。保留完整图，再依次强调各个主体。

**口述稿。**

> 前面我们分段完成了构图、核验、Skill 和安装。现在把它们连起来看：一句
> “作三角形、取中点”的要求，怎样变成一个可以保存、重载和拖动的文件？
>
> Agent 理解用户的文字，Skill 告诉它怎样操作。CLI 管理执行，GeoGebra 解释数学，
> 核验器把实际事实与请求声明比较。推理沿用宿主，本地工程没有再接一套模型服务。
>
> 接下来就沿一个完整请求，看看这些部分怎样配合。

**切换。** 从架构图中的“请求 JSON”进入
[triangle.json](../examples/triangle.json)。

### 4.2 请求：模型输出的不只有构图命令

**画面。** 依次展开 `source`、`choices`、`requirements`、`program`、
`checks`、`styles` 和 `interactions`，不一次展示整份 JSON。

**口述稿。**

> 这个完整案例要求作三角形 ABC，取 AB 的中点 M，连接 CM，设置红色和点名，
> 还要拖动 A 检查联动。
>
> source 保存原文。choices 单独保存初始坐标等演示选择，避免把系统自己的选择
> 当作用户条件。program 保存原生命令，例如 Midpoint 和 Segment。
>
> 请求还要说明怎样验收。checks 描述关系与依赖，styles 描述颜色和标签，
> interactions 声明真实拖动样本。requirements 把这些检查关联到要求。
>
> 这些都是调用方的声明，还不是成功证据。后面必须取得真实引擎事实。
> 检查清单有没有完整覆盖原题，也仍然需要对照原文复核。

**切换。** 沿[执行走读的调用链](triangle-execution-walkthrough.md#3-先看整条调用链)，
追踪这份请求怎样进入工具。

### 4.3 执行：沿四组代码找到事实来源

**画面。** 按下表切换。每个位置只解释一个职责，不逐行滚动源码。

| 定位点 | 本镜头解释的问题 |
| --- | --- |
| [request.ts](../src/request.ts) 的 `parseRequest`，入口见 [cli.ts](../src/cli.ts) | 请求在哪里被检查和拒绝？ |
| [viewer/engine.js](../viewer/engine.js) 的 `runRequest`、`snapshot` | 谁执行命令，事实从哪里读取？ |
| [verify.ts](../src/verify.ts) 的 `verifyChecks`、`verifyStyles` | 关系、依赖与外观怎样分别判定？ |
| [pipeline.ts](../src/pipeline.ts) 的 `runTool` | 谁组织执行、文件写入和资源生命周期？ |

**口述稿。**

> 请求先进入输入检查。这里检查 JSON 结构、对象引用、声明覆盖和执行边界。
> 通过之后，可信桥接把标签和表达式组合成原生命令，交给 GeoGebra。
>
> Midpoint 的数学含义由 GeoGebra 解释。TypeScript 不再实现一套中点算法。
> 引擎创建对象后，桥接读取对象类型、定义状态、依赖、坐标和样式，整理成事实。
>
> 核验器拿这些实际事实与请求比较，报告同时保留期望和实际结果。
> pipeline 负责组织各阶段，管理本次浏览器和输出目录。
>
> 要深入某个模块时，再进入详细设计。现在先用一个反例，看看这些边界有什么作用。

**切换。** 打开[静态中点反例](../examples/triangle-counterexample.json)，
与正例并排定位 M 的表达式。

### 4.4 反例：同一个位置，可以有不同的依赖

**画面。** 并排强调两条表达式，再展示 `midpoint` 的 `parents` 声明。

```text
正例：M = Midpoint(A,B)
反例：M = (3,0)
```

**口述稿。**

> 在这组初始坐标下，两种构造中的 M 可能位于同一个位置。但前者由 A、B 决定，
> 后者只是独立点。这个反例故意保留了中点依赖的验收要求。
>
> 原生事实会显示，静态点没有 A、B 这两个父对象。依赖检查因此失败，不能正式交付。
> 它在初态就会被拒绝，不必等到拖动后才发现问题。
>
> 这解释了为什么我们同时保留对象事实、关系检查和交互样本。截图看起来正确，
> 还不足以说明动态依赖正确。颜色也有自己的检查，不能用关系通过代替外观通过。

反例的具体规则见[架构中的核验说明](arch.md#如何通过-verifychecks)；
实际拒绝结果使用对应[验收记录](acceptance.md)，不要为串讲改写反例要求。

### 4.5 交付：什么时候才可以说完成

**画面。** 展示[详细设计中的提交阶段](details-design.md#13-pipelinets阶段执行与证据先行)，
再打开一份能与实际运行对应的交付目录。

**口述稿。**

> 这里有几个不同层级的“通过”。check 通过，只说明请求结构和声明覆盖符合要求，
> 没有启动引擎。当前阶段核验通过，也只说明这一阶段观察到的事实符合声明。
>
> build 还要完成导出、从磁盘独立重载，以及请求适用的真实交互。资源关闭和文件
> 复核也属于成功门禁。全部完成后，工具才提交正式交付目录。
>
> 在目录中，我们可以对照请求、事实、报告、GGB、截图和清单。GGB 是引擎导出的
> 原生构造包，截图则用于观察画面，两者用途不同。
>
> 最后，preview 复核并加载同一份交付 GGB，不重新执行命令画一张相似的图。
> ready 表示预览就绪；正常结束还要看 closed、退出结果和清理记录。

正式交付与文件复核见 [pipeline.ts](../src/pipeline.ts)、
[delivery.ts](../src/delivery.ts)；同文件预览见 [preview.ts](../src/preview.ts)。
失败分支与输出规则以[CLI 契约](demo-contract.md)为准。

### 4.6 扩展：换成圆内接正多边形

**画面。** 打开[滑块正多边形请求](../examples/circle-inscribed-polygon.json)，
强调 `Slider`、`Rotate`、`Polygon` 与对应检查。可插入已剪好的真实滑块变化片段。

**口述稿。**

> 换成圆内接正多边形，改变的是构图表达式、参数与检查声明。边数成为滑块，
> 顶点和多边形保留对边数的依赖。预检、执行、事实采集、导出重载和交付继续走
> 相同的管线，没有在工具里增加一个“看到多边形关键词就运行固定配方”的分支。
>
> 这次案例也把经验反馈给 Skill：需要变化的量，优先用原生滑块表达。
> 通用规则进入正文，具体构图片方进入示例。
>
> 这里仍要区分证据范围。自动样本覆盖初始 n 等于三；预览中的滑块变化是另一类
> 展示证据，不能直接宣称所有取值都经过自动核验。

### 4.7 收尾：给同事一张阅读地图

**画面。** 回到三份文档的分工表，最后展示[验收记录](acceptance.md)。

**口述稿。**

> 理解这个工程，可以沿着三样东西看：请求里声明了什么，引擎实际产生了什么，
> 最终交付保存了什么。
>
> 架构文档解释分工，三角形走读跟踪一次请求，详细设计帮助定位实现和失败边界。
> 想知道某项能力是否实际跑过，再到验收记录查对应日期、运行身份和结果。
>
> 同事接手后，可以先读一个完整请求，再看一个应当失败的反例，接着沿管线找到
> 事实与交付。这样既能理解为什么成功，也能知道失败时应该检查哪里。

## 6. 录制前统一口径

- 本稿以完整 `triangle.json` 为主。执行走读的原文不含拖动，使用其中的画面时，说明
  完整教学请求增加了拖动要求。不要把三个三角形请求当成同一次运行。
- 执行走读和旧总结稿中的部分完成状态属于历史描述。片尾当前状态从验收记录取用，
  不从架构图或未来录制计划推导。Codex 本地安装证据与双宿主、新会话首题、完整独立
  安装及发布验收应分别说明。
- 展示报告时，说明它对应的请求、阶段和运行。有限样本通过不等于一般数学证明。
- 展示失败修复时，引用[现有规则](arch.md#agent-接收失败后的修复流程)。规则存在
  不代表某次运行实际执行了修复，也不代表 CLI 内部有自动调用模型的循环。
- 将末尾可复用性审查明确称为后续建议，除非已有相应实现和验收记录。
- 安装根提供代码、依赖和运行时；workspace 保存本次请求与用户产物。
  展示安装路径与输出目录时，保持这一区分。

## 7. 录制完成后的检查

1. 每个镜头只放大当前讲解的字段、函数或报告部分，给观众留出阅读时间。

3. 口述中的成功层级与画面一致，未把 `check`、阶段报告或 `ready` 当作完整成功。
4. 历史素材标出所属阶段；当前状态与验收记录一致。
5. 片尾给出 README、架构、执行走读、详细设计、契约和验收记录的入口。
